# RECA Digital — модель работы с задачами через Codex

Статус: **проектирование**, без допуска к production и без автоматического выполнения. Основание: публичный лабораторный прогон AUTO-002, Actions run 39767982693; Draft PR #24 успешно создан контроллером и затем объединён человеком в `sandbox/reca-auto-control-setup`.

## Цель

Превратить разовую синтетическую цепочку в повторяемый управляемый процесс:

`Идея / баг / улучшение → оформленное задание → безопасный допуск → Codex → проверка изменений → Draft PR → человек принимает или отклоняет`.

Модель **не** получает права самостоятельно объединять PR, публиковать сайт, изменять секреты либо получать доступ к приватному `reca-digital/demo`.

## Роли и границы

1. **Владелец продукта** описывает цель, критерии приёмки и ограничения; явно санкционирует расходы на конкретный запуск.
2. **Issue (входящая задача)** содержит требования к UX/UI, затрагиваемые экраны, примеры, критерии приёмки и запрещённые изменения. Любые вложения и текст задачи считаются недоверенными данными.
3. **Gate** проверяет авторство, утверждение, версию контроллера, хеш задания, целевой коммит, доступный лимит попыток и уникальные защищённые receipt-теги. При расхождении — отказ.
4. **Codex** работает только с разрешённой копией тестового репозитория/заготовки и файловым allowlist; возвращает ограниченный набор файлов и объяснение, не получает write-token или production secrets. Для задач с кодом это **новый дизайн**, пока не реализован.
5. **Publisher** независимо проверяет выход: схему, пути, размер, отсутствие секретов, объём diff, целевой коммит. Публикует изменения только в новую ветку и **Draft PR** тестового репозитория.
6. **Человек** анализирует diff, UX, безопасность и результаты тестов; может запросить корректировку отдельным допуском либо объединить PR. Развёртывание — отдельный этап с отдельным разрешением.

## Предлагаемая структура Issue

- Контекст и пользовательская проблема.
- Ожидаемое поведение / пользовательский сценарий.
- Область изменений: точные файлы, экраны и разрешённая ветка.
- Критерии приёмки с конкретными проверками.
- Запреты и инварианты (что нельзя ломать).
- Источники/макеты (если есть).
- Допустимое число попыток и бюджет на этот Issue.
- Явное утверждение владельца; фиксируемый SHA-256 текста задания.

## Ступени внедрения

### A. Документирование (сейчас)

Сохранить эту модель в публичной лаборатории; не менять workflow, переменные или Issue labels. AUTO-002 закрыт: receipt `reca-auto-exec-002-initial-done` защищён, policy `enabled:false`.

### B. Реальная кодовая задача, но только на изолированной копии

Создать **новый отдельный sandbox-проект**, наполняемый вручную обезличенными исходниками и фиктивными данными. Новый контроллер должен разрешать только заранее перечисленные пути, делать независимую проверку diff, запускать тесты без секретов и создавать Draft PR только в sandbox. Никаких production URL, базы данных, webhook, токенов или пользовательских данных.

### C. Ревью и итерации

Владелец изучает Draft PR, запускает тесты и даёт замечания. Каждая оплачиваемая корректировка получает отдельное явное разрешение, выделенные receipt-теги и жёсткую привязку к конкретному PR/head SHA. Никакого молчаливого повторного запуска.

### D. Подключение настоящего проекта — отдельное решение

Только после ревью безопасности и явного решения владельца о конкретном репозитории и правах. По умолчанию `reca-digital/demo` остаётся **недоступным**. Автоматический merge и deployment запрещены.

## Требования к следующему прототипу

- Проходной тест без обращения к платной модели, где это возможно (mock/fixture, unit tests).
- Тесты fail-closed: неизвестный файл, небезопасный путь, подмена задания, смещение base SHA, повторная попытка, невалидный PR head, неразрешённое изменение.
- Новая уникальная серия receipt-тегов и предварительно активированная защита тегов без bypass.
- Отдельные разрешения чтения, генерации и публикации; запись GitHub разрешена только Publisher.
- Разделить отчёт о тестах, программные изменения и пользовательскую оценку; нельзя принимать код лишь по отчёту модели.
- Устойчивость к ошибкам при частичной публикации: явно сохранять одноразовость; никакого сброса тегов или повторного расхода.

## Критерий готовности

Одна одобренная тестовая Issue меняет только разрешённые файлы фиктивного проекта, проходит автоматические проверки, создаёт ровно один Draft PR; человек видит дифф и результаты тестов и вручную решает об объединении. Ни секреты, ни production, ни deployment при этом не затрагиваются.
